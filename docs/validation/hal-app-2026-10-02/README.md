# v0.2.0 HAL/APP 重构验证

日期：2026-10-02。工程 `E:/MCU/esp32/esp_mosicrokey`，ESP-IDF v6.1，目标 `esp32s31`。本轮采用[新 skill](../../../skills/embedded-hal-app/SKILL.md)：HAL 直接驱动硬件，APP 处理业务状态机，Task 负责等待与调度。旧 RTOS skill 的命名保留，强制硬件函数指针表和一次/二次业务划分取消。

## 实际改动

- 显示、SDMMC、按键、UART、音频控制 I²C 拆为五个实际 HAL，删除旧板级集合入口；SDK 句柄留在实现文件。
- UART 收行与业务解析分开；按键 HAL 返回类型化事件，扫描 Task 投递 APP；APP 和游戏 Task 的循环独立。
- 系统入口负责依赖组装；现有上游 Board/Codec override 和真实服务接口保留，原因见[架构](../../architecture.md)。没有为每个硬件再新增接口或工厂。
- 两个工作 Task 等待启动通知，全部创建成功才运行；部分创建失败可以安全回滚并重试。库刷新采用待处理标记，避免队列满时丢失完成通知。
- 源码导出与 TF 重挂使用同一个存储控制锁。SDK 释放 SD 上下文后即使返回错误，也不再保留已释放 card 句柄。
- 显示超时后先排空 DMA，不能确认完成时停止运行，避免提前修改仍被 DMA 使用的像素。完成通知等待为一秒，底层 SPI 提交和排空不承诺相同等待上限。

反复回归发现 Windows 游戏目录提交偶发 `errno=13 / win32=5`。仅主机 Windows 分支对拒绝访问、共享或锁冲突最多重试十次、间隔 10 ms；已有目标目录立即失败，设备仍单次 POSIX rename。实际 Windows 句柄不允许删除、25 ms 后释放的故障注入通过；已有版本的 sentinel 保持不变。随后五次游戏套件连续通过。自然失败的占用者未确定，不能归因于某个进程。Lua 时间、指令和内存限制没有放宽。

## 真实 Agent 游戏链路

模型请求 1 实际调用 `game_preview` 成功，但设备导出仅 84 B 空壳，未实现贪吃蛇。请求 2 的参考 ID 查找失败，最终 `status=1`，如实记录为失败。请求 3 提供完整参考源码并要求修改标题，真实 `game_preview` 发布 p2，最终 `status=0 backend_status=0`。发布成功和玩法满足需求分别检查，不能用模型总结替代源码和行为。

实际设备导出 p2 为 2829 B；同一受限 VM 的 32 项 Snake 行为检查全部通过，覆盖移动、得分、反向限制、失败/胜利、重开和密集食物搜索。参考玩法为穿墙版；本轮没有声称实现首条请求的撞墙失败变体。

设备进入游戏 `mode=4`，期间请求 4 成功回复 `GAME_BACKGROUND_OK`；三个完整十秒窗口均为 30.3 FPS。启动前和退出后的窗口包含空闲时间，分别报告 3.7/10.8 FPS，不作为持续运行帧率。方向串口输入后导出真实画布，全部 128 行及 FNV1a `331d2681` 校验成功，显示 HAL SNAKE、SCORE 1、绿色蛇身和食物，见[设备画布](evidence/device-game.png)。返回后 `mode=3`，Wi-Fi 在线、Agent 空闲、音频焦点 0。新增项目任务观测最小栈余量均超过 30%；这些是短时冒烟水位，不保证未执行场景。结果见 [record.json](record.json) 及对应日志。
