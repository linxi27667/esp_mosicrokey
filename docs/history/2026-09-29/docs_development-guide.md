# 开发指南

- 状态：草案
- 目标硬件验证：尚未记录

本文件记录协作者和 AI 修改项目时要遵守的工程流程。当前目录尚未包含固件工程结构，因此不预设组件目录或代码风格细节。产品目标要求同一固件搭载小智 AI 与 ESPClaw，并包含 TF 卡游戏创作/存取/运行闭环。

## 1. 工具链基线

- ESP-IDF：本机 v6.1，路径 `E:\MCU\esp32\.espressif\v6.1\esp-idf`。
- 工具目录：`E:\MCU\esp32\.espressif\tools`。
- Python 环境：`E:\MCU\esp32\.espressif\python_env\v6.1\venv`。
- ESP-IDF target：`esp32s31`；本机源码将其标记为 preview target，并选择 `IDF_ENV_BRINGUP`。
- 本机工具链可见该 target 不等于本项目固件已成功构建或目标硬件已验证。阶段 1 完成前，描述为“环境/target 配置已知”，不称为“板级支持已验证”。

## 2. 协作规则

1. 先查看相关需求、板级约束、架构和模块文档，再修改代码。
2. 仅实现当前明确范围；发现额外需求或复杂依赖时，先记录提案和影响。
3. 不编造 GPIO、板卡型号、存储容量或外设特性。
4. 对依赖上游代码的改动，记录仓库、版本/提交、许可证、依赖和本地修改边界。
5. 修改接口时同步更新架构和受影响模块文档。
6. 交付说明应写明修改文件、设计选择、验证结果和未验证事项。

## 3. 固件工程结构

待确定。工程目录创建后，根据首批功能和 IDF component 依赖设计最小结构；必须能在同一产品构建中纳入小智、ESPClaw、TF 游戏库和游戏入口/运行时。避免仅为预想中的扩展建立空层或空组件。结构决策记录在此，并在重大取舍时建立 ADR。

合并上游代码前，先锁定仓库和提交，记录主许可证、传递依赖许可证、构建方式、配置冲突、重复组件以及升级策略。

## 4. 构建、烧录与调试流程

目标板尚未确定，具体命令参数、端口、USB/串口方式和板级配置待确认。流程至少应覆盖：

1. 激活匹配的 ESP-IDF v6.1 环境。
2. 选择 `esp32s31` target 并配置工程。
3. 执行干净构建并记录配置和结果。
4. 通过目标板实际支持的 USB 或串口接口烧录。
5. 采集启动日志并记录板卡修订和工具版本。
6. 变更 target 或 sdkconfig 前备份并审阅配置变化。

本节不是已验证的目标板操作说明；目标板确定后再补充可直接复制的命令和故障排查。

## 5. 代码质量与验证要求

项目代码风格、静态检查、测试框架、日志级别、错误码、内存预算和 CI 尚待固件工程建立后确定。确定前采用小改动、明确假设、可观察错误和可复现验证的原则，不虚构硬性格式标准。

每次功能实现应记录：目标、验收方法、运行环境、构建/测试结果、资源数据（若相关）及未覆盖场景。

## 6. 安全与数据处理

联网、AI、语音、凭据和日志方案尚未确认。实现前需定义凭据存储、传输保护、用户数据保留、日志脱敏和断网行为。不得把密钥提交到源码或文档。
