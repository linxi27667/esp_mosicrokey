# ESPClaw 游戏创作与 TF 游戏库

- 状态：核心产品目标明确，生成格式和运行时待选型
- 关联需求：`GAME-01` 至 `GAME-04`
- 参考： [ESP-Mosaico 参考调研](../references/esp-mosaico.md)

## 1. 用户目标

用户通过设备上的 ESPClaw 描述游戏并迭代玩法；完成的游戏保存在 TF 卡；用户从 MosiCrokey 设备的游戏入口选择并打开游戏。游戏包和资源在重启后保留，增删/改游戏不应要求重刷主固件。

## 2. 主流程

```text
描述/修改游戏
    ↓
ESPClaw 产生游戏包
    ↓
检查清单、文件和运行时版本
    ↓
写入 TF 卡暂存区并完成校验
    ↓
原子切换为已安装游戏
    ↓
游戏入口枚举并显示
    ↓
用户选择 → 游戏运行时 → 退出回入口
```

这一流程是需求模型。具体 UI、目录和格式尚未确定。

## 3. 游戏包边界

候选游戏包至少需要定义：

- 唯一 ID、显示名称、版本、包格式版本和所需运行时版本。
- 游戏入口及其资源清单。
- 输入映射与目标屏幕参数（具体能力依板卡规格决定）。
- 可选音频资源、存档命名空间和资源上限。
- 游戏 API/能力声明，限定按键、显示、音频、文件和网络访问。

必须校验包格式、路径和大小；文件路径不能逃逸游戏目录。安装或更新使用临时文件/暂存区，校验成功后再标记可运行，避免中断后留下半包冒充有效游戏。

## 4. TF 卡行为

- TF 卡是游戏包和资源的持久介质，实际卡槽与总线由硬件设计确定。
- 记录挂载状态、容量、读写错误和游戏列表状态。
- 未插卡时游戏入口清晰提示，并保留设备其他功能。
- 卡空间不足、格式不支持、卡移除、文件损坏和写入中断必须可观察且可恢复。
- 当前运行游戏期间是否允许拔卡、是否支持热插拔，待产品定义；默认不假设安全热拔。
- 文件系统、目录布局、卡容量/速度等级和导入/导出方式待硬件与工作流评审。

## 5. 游戏运行时与 ESPClaw 产物

运行时必须能加载 ESPClaw 生成的游戏包，而不是只运行编译进固件的示例。候选方式：

- 设备端 Lua 或其他受限脚本引擎。
- 结构化游戏描述/专用 DSL 加固定解释器。
- PC 端将 Agent 生成的源码构建为设备兼容产物，再安装为 TF 游戏包。
- 以上方式组合。

[ESP-Mosaico Vibe](../references/esp-mosaico.md) 的公开游戏流程偏 PC 端 Agent + C 游戏 + Host 模拟器 + ESP-IDF 应用安装；可以借鉴模板、游戏 API 和 Host 验证，不等于支持 ESPClaw 在设备端生成 C 固件或 TF 动态加载游戏。

游戏运行时应限制无限循环、内存分配、文件访问和硬件控制范围，提供退出/超时机制。游戏崩溃不能导致设备无法回到主界面；实际隔离能力需依据运行时验证。

## 6. 验收用例

1. 通过 ESPClaw 创建一个最小可玩示例，并经格式检查。
2. 游戏包和资源成功安装到 TF 卡。
3. 断电重启后，游戏列表仍能发现该游戏。
4. 用户通过键盘/已确认控制器开始游戏、完成一轮游玩并退出到设备入口。
5. 重复安装/更新不破坏上一份有效游戏包；写入中断后可恢复或回滚。
6. 缺卡、坏包、空间不足和运行时错误都有用户可见提示。
7. 记录目标板运行时的帧率/响应、内存/PSRAM、TF 吞吐和功耗；阈值由产品指标另行确认。

## 7. 待确认

- ESPClaw 精确上游、可调用的创作能力和生成物格式。
- 目标游戏种类、最低画面/帧率、显示方向及输入方案。
- Lua/DSL/PC 编译等技术路线及其许可证、运行时大小和 IDF 兼容性。
- TF 卡槽、电气接口、文件系统、最大支持容量、格式化和热插拔策略。
- 存档是否进入 MVP；联网游戏是否允许。
