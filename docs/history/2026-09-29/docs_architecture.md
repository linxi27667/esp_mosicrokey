# 系统架构

- 状态：产品需求已明确；实现方案待设计/验证
- 更新：2026-09-29

MosiCrokey 的核心目标是同一台设备和同一产品固件同时提供小智 AI 与 ESPClaw，并让 ESPClaw 创作的游戏可保存至 TF 卡、由设备入口打开游玩。本文明确产品级边界和接口域；不在硬件未定时冻结 GPIO、任务优先级、内存分区或具体框架。

## 1. 已知平台事实

### ESP32-S31 芯片资料

乐鑫 ESP32-S31 预发布数据手册 v0.5（2026-07-13）描述双核高性能 RISC-V 系统、单核低功耗系统及 Sv32 两级页表地址转换，并列出 Wi-Fi、Bluetooth LE、Bluetooth Classic、802.15.4 等能力。具体模组/板卡是否暴露对应引脚、具体 IDF 版本的软件支持和本项目中的并发能力仍需核验。

### 本机开发环境

- ESP-IDF v6.1：`E:\MCU\esp32\.espressif\v6.1\esp-idf`
- 本机源码把 `esp32s31` 列为 `PREVIEW_TARGETS`，且对 `IDF_TARGET_ESP32S31` 选择 `IDF_ENV_BRINGUP`。
- Xiaozhi 上游目前说明 ESP-IDF v6.1 为推荐 SDK，且 S31 构建需要 IDF 6.1 或更新版本；需要固定版本/提交并本地验证。
- 当前公开 ESP-Mosaico BSP 要求 ESP-IDF 6.2 或更新版本，ESP-Mosaico Vibe 工作区使用固定 ESP-IDF master 提交。Mosaico 游戏栈与本机 v6.1 基线存在版本适配风险。

这些上游说明是随时间变化的；实施时应锁定仓库提交并复核 README、构建约束和依赖。

## 2. 产品级架构要求

1. **同固件双 AI**：单一产品固件中同时包含小智 AI 和 ESPClaw；两个入口都可在设备上访问，不通过重刷互斥固件切换。
2. **游戏创作闭环**：用户通过 ESPClaw 发起游戏创作/修改；系统把可运行的游戏包及资源保存至 TF 卡；设备游戏入口发现并启动它。
3. **游戏独立管理**：目标是更新/删除游戏无需重刷完整固件；文件格式、升级/回滚及存档细节待设计。
4. **统一设备交互**：键盘、右侧屏幕、音频和外接控制器服务可由各功能以明确生命周期使用；共享资源冲突需要由系统入口协调。
5. **可验证游戏 API**：游戏只能通过定义的输入、显示、音频、存档等游戏 API 工作；具体运行时和权限边界待决策。
6. **外部模型边界**：小智和/或 ESPClaw 可调用手机、局域网或云端模型服务；不要求 MCU 本地运行通用大模型。

“双功能同时搭载”已确定为产品要求。是否要求两个 Agent 在同一时刻后台都保持活跃，以及游戏运行时能否并行处理 AI 语音/网络请求，需形成单独的并发策略并以目标板实测。

## 3. 创作与游戏运行路径

```text
设备内 ESPClaw
   │ 用户描述、迭代游戏
   ▼
游戏生成/打包路径（格式、验证与安装接口待设计）
   │ 游戏包 + 资源
   ▼
TF 游戏库（持久化）
   │ 枚举、选择、启动
   ▼
游戏运行时 ── 游戏 API ── 键盘/摇杆、显示、音频
   │ 退出/存档
   └─────────────── TF 卡
```

关键路径验收必须覆盖“生成或修改 → 校验/保存 → 重启后仍可枚举 → 选择启动 → 可玩 → 正常退出”。仅生成 C/Lua 代码、仅保存文档或仅在 PC 仿真器运行均不满足设备端闭环。

### 候选技术路线（未选定）

- **设备端受限脚本/数据驱动运行时**：更接近设备 Agent 生成并将游戏包写到 TF 后直接加载的目标；需验证 ESPClaw 能力、脚本引擎、性能、内存和安全限制。
- **PC 端编译游戏应用**：Mosaico Vibe 公开路径使用 AI 编码 Agent、Raylib Lite、Host 模拟器和 ESP-IDF 构建，再将应用安装到设备；适合作为开发工作流参考，但与“ESPClaw 在设备上创建并写入 TF”的目标不同。
- **组合路径**：设备端 ESPClaw 产出受限描述/脚本，PC 工具或设备端运行时打包为版本化游戏包；需评估额外工作流和用户体验。

不因参考项目已使用某种引擎或脚本，就预先认定 MosiCrokey 必须照搬。

## 4. 系统上下文

```text
用户
 ├─ 键盘输入 ──────────────┐
 ├─ 屏幕交互/状态显示 ◀────┤
 ├─ 音频输入/输出（待确认） ┤  MosiCrokey 设备
 └─ 外接控制器（待确认）───┘
                              │
                 单一 ESP-IDF 产品固件（目标）
            ┌─────────────────┴─────────────────┐
       小智 AI 对话                         ESPClaw Agent
       网络/音频服务                        游戏创作/修改
                                                  │
                                                  ▼
                                   TF 游戏库 → 入口/运行时
                              │
                     Wi-Fi / Bluetooth / TF 接口
                              │
                     手机、局域网或云端服务（按需）
```

双 AI 与 TF 游戏链路是产品目标。模块、服务端、协议和游戏数据格式仍需设计；图中未确定的外设/链路不表示已选型。

## 5. 功能域与边界

| 功能域 | 初步职责 | 关键接口/问题 | 状态 |
|---|---|---|---|
| 设备入口 | 在小智、ESPClaw、游戏库和设置间导航 | 页面/功能生命周期、输入焦点、音频焦点 | 待交互设计 |
| 小智 AI | 提供小智对话体验 | 上游版本、板级适配、协议、资源 | 产品要求明确，集成待验证 |
| ESPClaw Agent | 自然语言设备交互并创作/修改游戏 | 与小智入口关系、产物接口、模型服务 | 产品要求明确，集成待验证 |
| TF 游戏库 | 持久保存并枚举游戏和资源 | TF 控制器、文件系统、包格式、异常恢复 | TF 存取为要求，硬件待定 |
| 游戏运行时 | 通过游戏 API 加载和运行游戏 | 运行时选型、性能、安全、游戏 ABI | 目标明确，待选型 |
| 输入服务 | 提供键盘及外接控制器事件 | 事件格式、扫描/去抖、游戏映射 | 键盘/外设资料待定 |
| 显示/音频服务 | 为 UI、AI 和游戏提供设备输出 | 资源仲裁、格式、焦点和并发 | 器件待定 |
| 网络服务 | 管理 Wi-Fi/蓝牙联网及请求 | 配置、凭据、并发、断网恢复 | 待定义 |

这些是产品和接口讨论的功能域，不代表已确定一对一固件组件或 FreeRTOS 任务。

## 6. 共享资源与并发约束

实现架构前，至少定义并验证以下场景：

- 小智 AI 与 ESPClaw 都编入固件、启动和切换入口。
- 小智会话活跃时进入 ESPClaw；是否保持小智后台音频/会话待产品确认。
- ESPClaw 写入 TF 卡时游戏入口、文件扫描或游戏运行的互斥行为。
- 游戏运行时对键盘、摇杆、屏幕、音频和 TF 的独占/共享关系。
- Wi-Fi、Bluetooth Classic、BLE、显示刷新和音频同时工作的限制。
- 游戏包写入过程中掉电/拔卡时的原子性和恢复策略。

RAM/PSRAM/Flash/TF 吞吐、CPU 负载、音频延迟、显示帧率、无线稳定性和供电必须基于实板和具体负载测量。

## 7. 暂不冻结

- 具体 ESP32-S31 订购型号、模组、板卡、屏幕、音频器件、引脚和 TF 控制器。
- ESP-IDF v6.1 是否继续作为最终版本，或为 Mosaico 游戏参考升级/移植到更新 IDF。
- 小智与 ESPClaw 的仓库、提交、集成方式和后台运行策略。
- 游戏内容使用 Lua、Raylib Lite、C 编译应用、专用 DSL 或组合方式。
- TF 文件系统、挂载点、目录布局、热插拔、卡格式化和损坏恢复。
- 游戏包清单、版本兼容、保存槽、导入/导出和删除交互。
- FreeRTOS 任务、核心亲和性、优先级、队列、同步方式与完整资源预算。

## 8. 架构评审输入

开始冻结实现前需要：

- 目标板资料及 TF 卡接口、电气和存储器件信息。
- 小智、ESPClaw 精确上游与版本组合，并在选定 IDF 上构建验证。
- 游戏创作产物格式、运行时、游戏 API 与保存/启动流程提案。
- 明确用户是否要求两 AI/游戏在同一时刻后台或前台并发。
- 典型游戏规格、显示目标、控制器输入、音频和资源测量。
