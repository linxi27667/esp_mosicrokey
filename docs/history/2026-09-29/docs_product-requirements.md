# 产品需求与范围

- 状态：初版草稿，待评审
- 项目：MosiCrokey
- 芯片目标：ESP32-S31（ESP-IDF target `esp32s31`）
- 软件方向：ESP-IDF + FreeRTOS（待目标硬件验证）

本文用于协作定义目标和边界。所有未核实的规格、依赖和技术选择均标为待确认或待调研。

## 1. 产品目标

设计并逐步实现一款面向对 AI 感兴趣的青少年的开源嵌入式设备。产品形态以键盘为载体，键盘右侧有屏幕，并探索 AI 对话、音频和游戏相关体验。

项目负责人负责硬件设计，并对软件约束和系统架构作决定；软件采用 vibe coding 协作方式推进。文档应使每一步都有明确需求、边界、接口和验收依据。

## 2. 用户与使用场景

### 目标用户

- 对 AI、编程或电子设备感兴趣的青少年。
- 参与硬件设计、固件开发和功能扩展的协作者。

### 目标场景

1. 用户通过键盘输入，并在设备屏幕查看状态和交互内容。
2. 用户探索联网 AI 对话；模型位置和服务方式待定，不假设 MCU 本地运行大模型。
3. 用户探索外接遥控器或摇杆作为游戏控制器。
4. 用户探索设备蓝牙音箱能力及其与 BLE 外设并用的可能性。
5. 用户通过设备端 ESPClaw 创作或修改游戏，将游戏包与资源保存到 TF 卡，再从设备游戏入口打开游玩；产物格式、运行时和创作流程细节仍待设计与验证。
6. 协作者依据文档中的职责、接口和约束共同扩展软件。

## 3. 功能拆分

### 3.1 键盘与屏幕交互

- 键盘扫描、电气连接、布局、扫描频率和输入事件接口待硬件方案确认。
- 屏幕型号、分辨率、总线、驱动、UI 框架和刷新需求待确认。
- 需定义启动、连接、错误和功能入口的最小状态反馈。

### 3.2 小智 AI 与 ESPClaw 双功能

本项目明确要求在同一台设备、同一产品固件中提供以下两项能力：

#### 双 AI 与游戏的核心验收项

| 编号 | 要求 | 验收口径 |
|---|---|---|
| AI-CO-01 | 小智 AI 和 ESPClaw 同时纳入一份产品固件 | 同一固件镜像包含两项功能，不需要擦写/重刷来切换 |
| AI-CO-02 | 设备提供两项功能的可达入口 | 用户能从设备界面进入小智对话和 ESPClaw 创作 |
| GAME-01 | ESPClaw 能参与创作/修改面向设备的游戏 | 输入创作需求后产生运行时可接受的游戏包，而非仅返回代码文本 |
| GAME-02 | 游戏包及资源写入 TF 卡并保留 | 写入成功后关机重启仍可被游戏库发现 |
| GAME-03 | 用户可从设备启动 TF 卡游戏 | 入口显示可用游戏；选择后进入游戏，能正常退出返回设备界面 |
| GAME-04 | TF/游戏错误可恢复 | 缺卡、坏包、空间不足、写入中断有明确提示，不破坏已有可用游戏 |

两个 AI 是否需要在同一时刻后台活跃，以及游戏运行时是否允许 AI 会话后台持续处理，属于后续并发策略；不能影响 AI-CO-01 至 AI-CO-02 的同固件共存要求。

1. **小智 AI**：提供小智项目定义的 AI 对话体验，具体语音/文本形态、服务端、账号与通信协议待结合所选上游版本确认。
2. **ESPClaw**：提供 ESPClaw 的设备端 AI Agent/Chat Coding 能力，允许用户通过自然语言创建或修改设备可运行的功能，重点包括游戏创作。

两项能力须共同集成到一个可烧录的产品固件中；用户应能在设备上进入两项功能，而不是通过擦写/烧录不同固件来切换。两个 Agent 是否需要在用户前台操作其中一个时仍保持另一个后台活跃，属于运行时并发需求，需在架构评审中确认并针对目标工作负载验证。资源规划必须将“双功能同固件”作为硬性目标，不能以资源风险为由默认退化为二选一固件。

需要调研和设计：

- 确认 ESPClaw 所指上游仓库、分支/版本和许可证；本轮资料检索参考了 [乐鑫 espressif/esp-claw](https://github.com/espressif/esp-claw)，但该引用仍需项目负责人确认。
- 确认小智上游版本和板级适配；[78/xiaozhi-esp32](https://github.com/78/xiaozhi-esp32) 当前项目说明提到 ESP-IDF v6.1 为推荐版本，并列出 ESP32-S31 构建支持，实际应锁定提交并自行复现。
- 选择合并方式（组件复用、功能模块移植或其他可维护方案），定义应用入口、生命周期和共享硬件资源的所有权。
- AI 模型推理是否依赖手机、局域网或云端；不默认在 MCU 本地运行大模型。
- 明确凭据、对话/语音数据、断网和服务端不可用时的行为。

### 3.3 音频与无线连接

- 明确“蓝牙音箱”的目标角色和使用方式（待确认）。
- 评估蓝牙音频、BLE 外设、Wi-Fi 并发时的协议角色、连接限制、带宽、内存、功耗和实际体验。
- 麦克风、扬声器、编解码器、放大器、音频接口与音频路径待确认。
- 数据手册列出的硬件能力不等于当前 IDF 对应软件路径已成熟；需按 v6.1 具体功能文档和目标板实测核验。

### 3.4 ESPClaw 游戏创作、TF 存储与游玩

核心产品需求：用户可以通过 ESPClaw 创作或修改面向本设备的游戏；生成的游戏必须能保存到 TF 卡，并能从设备上的游戏入口被选中、加载和游玩。不能将“生成了代码文本”视为游戏功能完成。

目标用户流程：

1. 用户在 ESPClaw 中描述游戏想法，并逐步创作或修改游戏。
2. 系统将符合设备游戏运行环境的游戏程序和资源写入 TF 卡。
3. 设备游戏入口枚举可用游戏并显示可识别的信息。
4. 用户选择游戏后，系统启动匹配的游戏运行环境，并把键盘/外接控制器输入、屏幕和可选音频交给游戏。
5. 用户退出游戏回到设备入口；若游戏支持存档，进度保存到 TF 卡并可再次载入（存档是否列入 MVP 待确认）。

必须定义的接口/约束：

- 游戏包格式、清单/版本信息、入口文件、资源目录和运行时 API。
- ESPClaw 输出如何经过语法/格式检查、资源限制和错误提示后安装。
- TF 卡文件系统、挂载点、卡未插入/读写失败/空间不足/文件损坏时的行为。
- 游戏启动、退出、崩溃恢复和返回系统入口的流程。
- 游戏对按键、摇杆、显示、音频和网络能力的访问范围。
- 生成内容须在受限游戏 API 中运行；不能默认允许任意生成代码直接访问任意 GPIO、系统文件、网络凭据或全量固件资源。

ESP-Claw 上游公开资料提到动态 Lua 加载和部分应用的 SD 卡可写存储；这是调研线索，不证明现成的游戏运行时或完整创作到游玩链路。[ESP-Mosaico 游戏开发](references/esp-mosaico.md)提供 PC Agent、模拟器和 C 游戏应用的参考流程，但没有确认其游戏存储在 TF 并由设备运行时独立加载。Lua/数据驱动游戏包、专用轻量游戏运行时、PC 构建后导出的包或其他格式均为候选，尚未决定。

遥控器/摇杆的连接方式、输入映射和断连行为待硬件方案确认；设备自身键盘是否承担全部游戏控制，待交互设计确认。

### 3.5 后续扩展

新增功能应先记录使用场景、依赖、资源需求、接口和验收方式，再进入实现；未经讨论不扩大当前阶段范围。

## 4. 系统边界

### 设备端

规划由 ESP-IDF 固件负责启动、实时输入、屏幕交互和已确认的板载外设。具体任务划分、优先级和内存预算须等板卡与外设规格确定后设计。

### 外部服务

AI 对话、内容生成或管理能力可能依赖手机应用、局域网服务或云服务。部署位置、账号和凭据、网络安全、数据保留与断网降级方式均待确认。

### 操作系统与 MMU 说明

乐鑫 ESP32-S31 预发布数据手册 v0.5 列出 Sv32 两级页表地址转换，因此不能继续使用“ESP32-S31 没有 MMU”作为结论。该硬件事实本身也不能证明通用 Linux/Ubuntu 已有可用启动链、驱动、长期维护支持或符合本项目需求。本项目当前按 ESP-IDF + FreeRTOS 固件规划；若未来考虑 Linux，应作为单独技术验证和架构决策，不视为当前承诺。

ESP-IDF v6.1 本机源码将 `esp32s31` 标为 preview target，并启用 `IDF_ENV_BRINGUP`。应关注预览阶段 API/功能成熟度和目标板适配情况。

### 烧录与远程管理

开发初期以 ESP-IDF 构建、串口/USB 烧录和串口日志为主。远程管理或调试若有需求，应作为固件中的受控网络能力评估，不将其描述为板上 Linux 主机的 SSH 能力。

## 5. 非目标与暂不承诺

- 当前不承诺在 MCU 上运行通用大语言模型。
- 当前不承诺运行通用 Ubuntu/Linux；MMU 存在与否不能单独决定操作系统支持结论。
- 小智 AI 与 ESPClaw 同属产品固件的目标范围；具体合并方案和后台并发行为尚未验证，不承诺未经测试的并发性能。
- 当前不承诺蓝牙音频、BLE 外设、Wi-Fi、显示、双 AI 能力和游戏运行时可在所有工作负载下同时稳定运行；并发组合必须实测。
- TF 卡存储和读取游戏包是产品需求；具体卡槽/接口、电气设计、容量/格式与驱动方案尚未冻结。其余板卡、模组、存储容量、屏幕、音频器件、引脚或供电方案也待确认。
- 当前不承诺云服务、账号体系、远程 SSH 或公网管理方案。
- 未经调研不承诺任何上游项目的许可证适用性或可再发布性。

## 6. 资源与集成风险

在硬件和具体软件路径确定后评估以下事项：

- 芯片内部 RAM、PSRAM、Flash 容量、带宽和可供应用使用的余量。
- 显示缓冲区、音频缓冲区、网络栈和游戏运行时之间的内存/CPU/总线竞争。
- Wi-Fi、Bluetooth Classic、BLE（含目标音频模式）的软件支持、共存、角色和并发限制。
- 键盘扫描延迟与显示、无线、音频任务的实时性竞争。
- 游戏运行时的帧率、资源格式、存储和调试需求。
- 峰值电流、电池/稳压设计、射频发射、音频输出带来的供电与热设计要求。
- 上游许可证、依赖版本、更新策略、服务端依赖和维护成本。

数据手册 v0.5 给出了芯片级规格；它是预发布版本，且具体产品资源由芯片型号、模组和开发板实现决定。资源预算必须以实际硬件资料和测量结果为准。

## 7. 待确认事项

### 产品与硬件

- 目标用户的年龄范围、主要教育/娱乐场景和 MVP 优先级。
- ESP32-S31 的具体芯片订购型号、模组或开发板，以及硬件资料版本。
- Flash/PSRAM 配置、可用 GPIO、引脚复用、电源、电池、散热和调试接口。
- 屏幕型号、尺寸、分辨率、接口及触控需求。
- 键盘矩阵/直连方案、按键数量、背光和输入法需求。
- 音频输入/输出器件及“蓝牙音箱”的具体目标角色。
- 外接控制器的有线/无线方式和连接器方案。

### 软件与服务

- 第一阶段最小可交付功能与明确优先级。
- ESP-IDF v6.1 目标板构建、烧录和关键外设驱动验证情况。
- 小智与 ESPClaw 的上游版本、许可证、依赖、资源和平台适配结论。
- AI 服务端位置、网络条件、密钥管理、隐私和费用承担方式。
- UI、音频和游戏运行时的技术选择与版本。
- 是否需要离线交互，以及离线范围。

### 发布与协作

- 代码托管和项目开源许可证待确认；本初版文档不代表授权创建远程仓库或推送发布。
- 用户数据、语音、对话记录、日志和凭据的处理策略待确认。
- 贡献流程、代码风格、构建环境和硬件验收设备待确认。

## 8. 里程碑与验收标准

### 阶段 0：需求与硬件基线

交付：评审后的范围、目标板卡/外设清单、更新后的 `board-contract.md`，并将 TF 卡读写列入板级设计。

验收：关键硬件参数有对应资料或测量来源；未确认项继续显式标记；明确 MVP 和阶段优先级。

### 阶段 1：目标板与开发环境验证

交付：最小 ESP-IDF 工程、构建/烧录/日志说明，以及对 preview target 限制的记录。

验收：在选定目标板上可复现配置、构建、烧录和启动；结果注明 ESP-IDF 版本、板卡修订和验证步骤。只有 target 列表中存在 `esp32s31` 不算板级验证完成。

### 阶段 2：基础交互与 TF 卡

交付：键盘输入到屏幕反馈的最小端到端功能，以及 TF 卡挂载、文件枚举、读写的基础验证。

验收：交互可重复验证；测试卡的插入、读写错误和重启后数据保留行为有记录。

### 阶段 3：同固件双 AI 能力

交付：小智 AI 与 ESPClaw 在同一产品固件中的集成原型及设备内功能入口。

验收：单一固件镜像同时包含两项能力；用户无需重刷即可进入小智对话和 ESPClaw；记录构建方式、上游版本、许可证、依赖、服务端边界、资源占用和未支持的运行时并发场景。

### 阶段 4：ESPClaw 到 TF 游戏的端到端流程

交付：选定游戏格式/运行环境后的最小创作、保存、目录发现、启动、游玩和退出流程。

验收：通过 ESPClaw 创建的样例游戏及其资源写入 TF 卡；设备重启后游戏仍可被游戏入口发现并启动；错误包、空间不足和 TF 读写失败有可见错误与安全退出行为。若 MVP 包含存档，需验证存档重启后可恢复。

### 阶段 5：双 AI、游戏及外设集成

交付：目标工作负载组合的资源评估及联调记录。

验收：明确小智对话、ESPClaw Agent、游戏、显示、音频和无线的并发/切换条件；在目标板测量响应、内存余量、掉帧/音频中断、功耗和稳定性，并记录产品可承诺的使用方式。

### 阶段 6：集成与发布准备

交付：已选功能的集成版本、用户/开发者文档和发布清单。

验收：目标功能有可重复的测试/验收步骤；硬件要求、外部服务、许可证、隐私和已知限制均有记录。发布行为需另按项目托管与发布决策执行。

阶段可按硬件与调研结果调整；开始每阶段实现前，应能审阅其范围、依赖和验收标准。
## 9. 文档状态规则

- **已确认**：有用户决策、正式硬件资料或明确实测依据。
- **待调研**：需要查阅上游资料、许可证、源码或开展验证。
- **待确认**：需要项目负责人作产品或硬件决策。
- **已验证**：写明环境、版本、板卡和复现步骤的实测结论。

更新结论时保留必要依据和日期；不把旧对话中的未经核验说法升级为事实。
